# PASSRESS MIS — Technical Documentation Package

Phase 7 deliverable: the master index tying together every table, column,
relationship, DAX measure, Power Query, worksheet, and dependency in the
workbook. This file is the **catalog** — for full depth on any one layer,
follow the pointer in that section to the file that's owned it since the
phase that built it (no content is duplicated wholesale; this indexes and
cross-references rather than forking a second copy that can drift).

Current state: **58 sheets** (15 visible, 43 hidden), **72 Excel Tables**,
**39 named ranges** (21 single-cell + 18 list/table-column), **40 Power
Query files**, **~90 DAX measures**. Generated by
`scripts/build_workbook.py`; regenerate with `python3 build_workbook.py`.

**Naming lifecycle — read before wiring Power Query:** every `RAW_`/`LOG_`
table above is a **placeholder** named `tbl_<code>` (e.g.
`tbl_RAW_Variants`). Once Power Query is wired per `DEPLOYMENT_GUIDE.md`
§5, the placeholder is deleted and the live table Power Query creates is
named after the **query**, with no `tbl_` prefix (`RAW_Variants`). Every
DAX measure, and every worksheet formula as of Phase 7, already assumes the
post-wiring name — see `PHASE6_PRODUCTION_READINESS_REVIEW.md` §10.1 for
the bug class this convention exists to prevent. Manual-entry tables
(`tbl_ProductCostMaster`, `tbl_ManualExpenses`, etc.) never go through this
lifecycle — their `tbl_` prefix is permanent.

## 6. Relationships (Data Model)

Reproduced from `dax/README.md` Step 4 (that file remains the setup-order
authority; this is the reference copy for quick lookup). All single-
direction, one-to-many, Dimension → Fact:

| From (one side) | To (many side) |
|---|---|
| `DIM_Date[DateKey]` | `FACT_OrderLines`, `FACT_Refunds`, `FACT_Payments`, `FACT_InventoryMovements`, `FACT_ManualExpenses`, `FACT_CapitalTransactions`, `FACT_PurchaseOrderHeader`, `FACT_GoodsReceipt` (all `[DateKey]`) |
| `DIM_Product[ProductKey]` | `FACT_OrderLines[ProductKey]`, `FACT_PurchaseOrderLines[SKU]`, `FACT_GoodsReceipt[SKU]`, `FACT_InventoryMovements[ProductKey]`, `FACT_ManualExpenses[RelatedSKU]` |
| `DIM_Product[PrimarySupplierID]` | `DIM_Supplier[SupplierKey]` |
| `DIM_Customer[CustomerKey]` | `FACT_OrderLines[CustomerKey]` |
| `DIM_Location[LocationKey]` | `FACT_OrderLines[LocationKey]`, `FACT_InventoryMovements[LocationKey]` |
| `DIM_Collection[CollectionKey]` | `FACT_ManualExpenses[RelatedCollection]` |
| `DIM_Supplier[SupplierKey]` | `FACT_ManualExpenses[SupplierID]`, `FACT_PurchaseOrderHeader[SupplierID]` |
| `FACT_OrderLines[OrderLineKey]` | `FACT_Refunds[OrderLineKey]` (fact-to-fact) |
| `FACT_PurchaseOrderHeader[PONumber]` | `FACT_PurchaseOrderLines[PONumber]`, `FACT_GoodsReceipt[PONumber]` (fact-to-fact) |

**`DIM_ProductCostHistory` has no Data Model relationship** — the SKU +
effective-date-range join it needs isn't expressible as a Power Pivot
equality relationship; it's resolved in Power Query instead
(`fn_GetEffectiveCost`, called from `FACT_OrderLines.pq`). See
`dax/README.md` for the full reasoning.

## 7. Dependency graph

```
Shopify Admin GraphQL API
        │
        ▼  fn_ShopifyGraphQL / fn_ShopifyPagedConnection / fn_IncrementalWindow
   RAW_ staging tables (10) ──────────────┐
        │                                  │  LOG_RefreshHistory / LOG_DataQuality
        ▼  + fn_GetEffectiveCost            │  (fn_AppendLog, depends on all RAW_
   DIM_/FACT_ star schema (17) ◄── manual   │   queries completing first)
        │                        entry      │
        │                        tables     ▼
        │                        (05,08,   14_Data_Quality dashboard,
        │                        10,11,12) 01_Home status cards
        ▼
   Data Model relationships + DAX measures (~90, dax/MEASURES.md + addenda)
        │
        ▼  CUBEVALUE / CUBESET / CUBERANKEDMEMBER
   02_Partner_Dashboard, 03_CEO_Dashboard, BI_Insights, BI_Alerts,
   BI_Forecast, BI_HealthScore, RPT_ExecutiveBrief, RPT_Workflow
        │
        ▼  direct cell references (not re-derived CUBE formulas)
   Dashboards' "Key Insights" / "Alerts" / "Forecast" sections
```

**Manual-entry tables are a parallel input path**, not downstream of
Shopify: `10_Expenses`, `11_Capital`, `12_Suppliers`, `05_Products`'
Product Cost Master, `08_Finance`'s Budget, and `15_Settings`' KPI
Targets/Health Score Weights/Holidays all feed the star schema or DAX layer
directly, independent of whether Power Query has been wired yet (though
some — Product Cost Master's SKU dropdown, Expense's SKU/Collection
dropdowns — do depend on `RAW_Variants`/`RAW_Collections` being wired for
their dropdown lists to populate).

**Circular dependencies**: none exist by design — verified in
`PHASE6_PRODUCTION_READINESS_REVIEW.md` §10.5 and re-confirmed in this
phase's review (`PHASE7_FINAL_ARCHITECTURE_REVIEW.md` §1); the Data Model
has no mechanism to read back into worksheet cells, which makes a cycle
through `BI_HealthScore` (the most interconnected sheet) structurally
impossible, not just untested.
